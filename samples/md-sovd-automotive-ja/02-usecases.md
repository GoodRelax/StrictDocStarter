# SOVD ユースケース (Use Cases)

**Grammar**: sovd-grammar.sgra
**UID**: DOC-SOVD-USECASES
**Version**: 1.0

本書は SOVD 車両診断システムの **ユースケース** (アクターがシステムを使って目標を達成する
利用シナリオ) を定義する。 **本書の UC は要求の親である。**
`01-stakeholder-requirements.md` の各ドメインの要求が UC を `Parent` で指し、
受入テスト (`10-test-spec.md` の AT 系) が UC を検証する。

**要求と UC の区別 (ISO/IEC/IEEE 29148 / A-SPICE):** 「システムが満たす条件」は要求 (EARS、
`01-stakeholder-requirements.md`)、 「アクターがどう使うか」は本書 (シナリオ) である。
29148 はユースケースを利害関係者要求の表現技法として扱い、 システム要求はそこから
導出されるものとする。 だから線は 要求 → UC (導出) と 受入テスト → UC (検証) の
2 方向に向く。 **`Parent` は常に具体から抽象へ向く。**

**アクター (Actors)**

| アクター              | RBAC ロール     | 説明 / 主な関心                                                                               |
| --------------------- | --------------- | --------------------------------------------------------------------------------------------- |
| 整備士                | `Mechanic`      | 出先・工場から遠隔で車両を診断する。 データ読出・DTC 取得 / クリアを行う。                    |
| OEM エンジニア        | `OEMEngineer`   | 全診断機能に加え、 個人情報を含む DID へのアクセスや OTA 更新の実施が可能。                   |
| フリート運用者        | `FleetOperator` | 多数車両の状態を遠隔で一括監視する (主に読み取り)。                                           |
| OEM バックエンド      | (システム)      | トークン発行・失効リスト配信・更新パッケージの署名 / 配信・DTC マスタ提供を担う外部システム。 |
| 攻撃者 (脅威アクター) | (なし)          | なりすまし・盗聴・改ざんを試みる。 認証・認可・暗号 (UC-001) で防御する対象。                 |

**ユースケース図 (アクターとユースケース)**

UC-001 は全 UC の前提となる「認証・認可の土台」。 攻撃者の脅威 (なりすまし等) は UC-001 で
防御し、 OEM バックエンドがトークン・失効・署名の信頼基盤を供給する。

**上の要求はすべて `01-stakeholder-requirements.md` にある。**
そこから各ドメイン文書の L1 以下が伸びる。

**4 件は 1 本の筋でつながる。** 車両に異常が生じ、 関係者が遠隔から認証を受け (UC-001)、
システムが役割に応じた認可範囲を判定する。 関係者は車両データの読み取り (UC-002) や
故障コードの取得 (UC-003) で原因を調べ、 必要なら故障コードのクリア (UC-003) や
ソフトウェアの遠隔更新 (UC-004) を実施する。 前提は、 車両が TCU 経由でクラウドに
接続でき、 関係者が有効な資格情報を持つことである。 工場へ入庫せずに車両の問題が
片づく — それが `SYS-L0-001` の言う「提供」の中身である。

**全体をまとめる凧レベルのユースケースは置かない。** 4 件を 1 件にまとめても
上の筋の言い換えにしかならず、 段が 1 つ増えるだけである。 本書は海面レベル
(利用者の目標 1 つで完結する高さ) だけを扱う。 全体像はこの筋と `SYS-L0-001` が担う。

## UC-001 認証・認可 (Authentication & Authorization)

**Type**: SECTION

### 整備士による遠隔・認証付き診断アクセス

**Type**: REQUIREMENT
**UID**: UC-001
**TYPE**: UseCase
**ASIL**: QM
**LAYER**: L0_Stakeholder

**Statement**:

**アクター:** 整備士 (主)、 ドライバー、 OEM バックエンド (トークン発行)、 SOVD システム。

**事前条件:** 整備士が有効な資格情報を持ち、 車両が遠隔到達可能である。

**主成功シナリオ:**

1. 車両が故障し、 警告灯が点く。
2. ドライバーが整備士に遠隔診断を依頼する。
3. 整備士が SOVD クライアントで認証する (OAuth 2.0 PKCE)。
4. システムがアクセストークン (JWT) を発行する。
5. 整備士が Bearer トークンを付けて診断リソースを要求する。
6. システムがトークンとスコープを検証し、 認可された範囲でアクセスを許可する。

**事後条件:** 整備士が認可された範囲で車両診断にアクセスできる。

**代替フロー:** 未認証 → 401 で拒否。 スコープ不足 → 403。 失効トークン → 401。

**VERIFICATION**: 認証済みクライアントで診断リソースの GET が HTTP 200 を返し、 対象データが
取得できること。

**Relations**:

- **Type**: `Parent`
  **ID**: `SYS-L0-001`

## UC-002 車両データアクセス (Vehicle Data Access)

**Type**: SECTION

### 車両データの遠隔読み取り

**Type**: REQUIREMENT
**UID**: UC-002
**TYPE**: UseCase
**ASIL**: QM
**LAYER**: L0_Stakeholder

**Statement**:

**アクター:** 整備士 / OEM エンジニア (主)、 SOVD システム。

**事前条件:** 認証済みで read:did スコープを持つ。

**主成功シナリオ:**

1. 整備士が車両の現在状態 (走行距離・電圧・各 ECU 温度等) を確認したい。
2. 整備士が対象の DID を指定して読み取りを要求する。
3. システムがスコープを検証する。
4. システムが DID を担当 ECU へ解決し、 UDS ReadDataByIdentifier へ変換する。
5. ECU が値を返す。
6. システムが ASAM SOVD JSON に変換して整備士へ返す。

**事後条件:** 整備士が車両データを把握できる。

**代替フロー:** 個人情報 DID へ Mechanic がアクセス → 403。 周期購読・スナップショット・
バルク転送も同じ認可フローに従う。

**VERIFICATION**: 認可されたクライアントで代表的な DID 群が取得でき、 未認可の項目は返らないこと。

**Relations**:

- **Type**: `Parent`
  **ID**: `SYS-L0-001`

## UC-003 故障診断 (DTC)

**Type**: SECTION

### 故障診断 (取得・クリア)

**Type**: REQUIREMENT
**UID**: UC-003
**TYPE**: UseCase
**ASIL**: QM
**LAYER**: L0_Stakeholder

**Statement**:

**アクター:** 整備士 (主)、 SOVD システム。

**事前条件:** 認証済みで read:dtc (取得) / write:dtc (クリア) スコープを持つ。

**主成功シナリオ:**

1. 整備士が、 警告灯の点いた車両の故障原因を調べたい。
2. 整備士が故障コード (DTC) 一覧を要求する。
3. システムが UDS 0x19 で各 ECU の DTC を集約し、 ステータス付きで返す。
4. 整備士が原因を特定し、 修理を行う。
5. 修理後、 整備士が対象 DTC のクリアを要求する。
6. システムが車速ゼロを確認し、 UDS 0x14 でクリアする。

**事後条件:** 故障コードが取得され、 (停車中なら) クリアされる。

**代替フロー:** 走行中のクリア → 409 で拒否。 フリーズフレーム取得も同フロー。

**VERIFICATION**: 代表的な DTC が、 status (active/pending/confirmed/permanent) 付きで取得できること。

**Relations**:

- **Type**: `Parent`
  **ID**: `SYS-L0-001`

## UC-004 ソフトウェア更新 (OTA)

**Type**: SECTION

### OTA 遠隔ソフトウェア更新

**Type**: REQUIREMENT
**UID**: UC-004
**TYPE**: UseCase
**ASIL**: QM
**LAYER**: L0_Stakeholder

**Statement**:

**アクター:** OEM エンジニア / OEM バックエンド (主)、 ドライバー、 SOVD システム。

**事前条件:** 署名付きの更新パッケージが用意され、 車両が更新を受け取れる。

**主成功シナリオ:**

1. OEM が不具合修正ソフトを車両へ配信したい。
2. OEM バックエンドが署名付き更新パッケージを配信する。
3. システムがパッケージをダウンロードする。
4. システムが署名を検証する。
5. システムが走行状態 (停車・シフト P・パーキングブレーキ) を確認し、 非アクティブ側へ書き込む。
6. ブートローダ切替で新バージョンが起動し、 進捗をドライバーへ通知する。

**事後条件:** ECU が新しいソフトウェアバージョンで動作する。

**代替フロー:** 署名検証失敗 → 破棄。 走行中 → 書込延期。 書込失敗 → 旧版へロールバック。

**VERIFICATION**: 署名付きパッケージの配信 → 適用 → 進捗確認が一連で行え、 適用後に新バージョンで
起動すること。

**Relations**:

- **Type**: `Parent`
  **ID**: `SYS-L0-001`
